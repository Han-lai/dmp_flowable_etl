# 指標明細驗證說明

> 本文件說明：KPI 報表的數字是怎麼來的、明細檔怎麼產生與取得、包含哪些資料、哪些被排除了，以及如何用明細檔反查驗證報表數字。

---

## 一、明細檔怎麼來的（產出流程）

明細檔**不是**直接從資料庫下載，而是經過「ClickHouse 運算 → 寫到 S3 → 下載解壓縮 → 另存為 Excel」四個步驟：

| 步驟 | 說明 |
|---|---|
| ① ClickHouse 運算並寫出 | 在 ClickHouse 伺服器上執行匯出程式，直接算好每一列的日/週/月結算狀態，壓縮成 `.csv.gz` 寫到 S3 |
| ② S3 存放 | 依環境分別存放於三個 S3 環境（見下表），每個 KPI 組合（月份 × 區域 × 廠別 × 流程別）各自一個檔案 |
| ③ 下載解壓縮 | 從 S3 下載對應環境的 `.csv.gz`，解壓縮得到 `.csv` |
| ④ 另存為 Excel | 用 Excel 開啟 `.csv`，另存新檔為 `.xlsx`，方便篩選與樞紐分析 |

**S3 環境對應表**（主機見 `infra/.env`，bucket 依環境區分）：

| 環境 | Bucket |
|---|---|
| dev（開發） | `dmp-lakehoused` |
| qas / uat（測試） | `dmp-lakehouseu` |
| prd（正式） | `dmp-lakehousep` |

**驗證時請確認你拿到的檔案來自正確環境**——同一個月份組合在 dev/qas/prd 三邊都可能各自存在一份，數字若對不上，第一步先確認是不是比對到不同環境的檔案。

## 二、明細檔結構與涵蓋範圍

### 檔名規則

```
{年-月}_{region}_{plant}_{vx_type}.csv.gz  （及對應的 .xlsx）
```

例：`2026-04_CNE_WJ2_V2.csv.gz` = 2026 年 4 月、CNE 區域、WJ2 廠、V2 流程的明細。

一個檔案只對應**一個月份 × 一個區域 × 一個廠別 × 一個流程別**的組合，不是把一整區域的所有月份塞進同一個檔案的不同 Sheet。

### 目前涵蓋範圍

資料來源為 `silver.mv_fact_task_vx`，實際涵蓋 **2025-10-08 起**的資料，上限跟隨 ClickHouse 目前已同步的資料進度（同步進度請洽維運人員確認目前最新日期，不同批次匯出的涵蓋上限可能不同，**不要以文件上的日期為準**）。

已知目前有資料的區域/廠別組合：CNE（MS/WJ2/WJ4/WJ5）、CNS（DG2/DG3/DG7）、CNW（CQ1）。不同廠別開始有資料的月份不同——這是產線陸續上線的正常現象，不是缺漏。

## 三、明細檔與 KPI 報表的對應關係

KPI 報表（金層）的每一個數字，都可以在對應月份的明細檔中找到相符的任務記錄。

**驗證邏輯**：
- 報表的「**Total**」= 明細中同一線別、同一期間**且 `in_month_cohort = 1`** 的資料列數（見第四節說明為何要加這個條件）
- 報表的「**Done**」= 篩選後 `status_daily` / `status_weekly` / `status_monthly` 欄位值為 `DONE` 的列數
- 報表的「**Todo**」= 值為 `TODO` 的列數
- 報表的「**Doing**」= 值為 `DOING` 的列數

> 篩選時請根據報表的時間粒度選擇對應的欄位，說明見下方第四節。

## 四、關鍵欄位：`in_month_cohort` 與 `file_month`（務必先讀）

這是最容易造成驗證數字兜不起來的地方，比日/週/月欄位選錯更常見。

### 為什麼一個檔案裡會出現「別月開單」的任務？

KPI 報表的**日粒度**在 2026-04-01 前後採用不同語意：

| 期間 | 日粒度語意 | 對明細檔的影響 |
|---|---|---|
| **2026-04-01 之前** | 事件日：當天只要有「開單、簽收、完工」任一動作就算 | 一筆 2 月開單、3/31 完工的任務，**也會出現在 3 月的檔案裡**（因為 3/31 有完工動作） |
| **2026-04-01 之後** | 開單日 cohort：只算開單當天 | 只出現在開單月的檔案裡，不會跨月出現 |

如果只用「開單月」分檔，2026-04-01 之前的月份會漏算這些跨月完工的任務，畫面數字就對不起來。因此**在 2026-04-01 之前**，同一筆任務可能同時出現在 2～3 個不同月份的檔案裡。

### 兩個欄位的作用

| 欄位 | 說明 |
|---|---|
| `in_month_cohort` | `1` = 這筆任務**本月開單**；`0` = 這筆任務是別月開單、因為本月有簽收或完工動作才補進來的 |
| `file_month` | 這筆列所屬的檔案月份（除錯用，可確認自己開對檔案） |

**⚫ 驗證週粒度、月粒度時，務必加篩選 `in_month_cohort = 1`，否則會把跨月補進來的任務重複算進去，數字會偏高。**

**⚫ 驗證日粒度時不需要篩這個欄位**——因為日粒度本來就是要抓「當天有動作」的任務，跨月補列正是為了讓日粒度算得準。

## 五、日 / 週 / 月的結算狀態欄位不同

明細中有三個專用欄位，分別對應不同的報表粒度：

| 報表粒度 | 應看的欄位 | 結算截止點 |
|---|---|---|
| **日報** | `status_daily` | 開單/簽收/完工當天（依上述兩種語意判斷） |
| **週報** | `status_weekly` | 開單當週**週日** 23:59:59 |
| **月報** | `status_monthly` | 開單當月**最後一天** 23:59:59 |

### 同一筆任務，三個欄位的值可能不同

舉例：某任務 1/28（週二）開單，2/3（隔週一）才完工

| 欄位 | 值 | 原因 |
|---|---|---|
| `status_daily` | `TODO` | 1/28 當天沒有任何動作 |
| `status_weekly` | `TODO` | 在 2/2（週日）之前未完工 |
| `status_monthly` | `DONE` | 在 1/31 月底前完工 ✓ |

### 什麼是「開單日」？

KPI 的時間基準是**開單日（`task_start_date`）**，不是完工日。一張 12/30 開出的工單，即使 1/5 才完工，它仍然算在 **12 月**的報表裡。

## 六、哪些任務被排除、不計入 KPI

以下類型的任務不納入 KPI 計算，也**不會出現在明細檔中**：

| 排除原因 | 說明 | 如何識別 |
|---|---|---|
| **自動跳過節點** | 流程中系統自動完成、無需人工介入的步驟 | 任務被標記 `autoComplete = 1` |
| **系統帳號操作** | 處理人為 SYSTEM，非真實人員操作 | `assignee_name = 'SYSTEM'` |
| **系統流程節點** | 流程引擎內部的自動化路由節點 | 任務代碼以 `E` 或 `C` 開頭 |
| **Q 測試工單** | 品質驗證用的測試單，非正式生產 | 工單號以 `Q` 開頭 |
| **R 測試工單** | 維修驗證用的測試單，非正式生產 | 工單號以 `R` 開頭 |
| **通知任務** | 純通知性質，無需人工處理 | 任務名稱含 `Notify` |
| **虛擬任務** | 流程設計用的佔位任務 | 任務名稱含 `Dummy` |

## 七、V1 / V2 / V3 的分類規則

明細檔依 `vx_type` 欄位分檔，分類規則如下：

### V1 — 標準生產流程

包含以下情況，**任一符合即歸 V1**（優先順序由上到下）：

1. **NPE 廠區的非出貨任務**：工廠為 NPE，且任務代碼**不是** V2 開頭 → 強制歸 V1
2. **特殊工單前綴**：工單號前三碼為 `196`、`199`、`200`、`210`、`212`、`213` → 歸 V1
3. **任務代碼 V1 開頭**：標準 V1 流程

> **為什麼 NPE 廠區要特別處理？**
> NPE 廠區的流程雖然在系統中以 V3 代碼建立，但業務性質與 V1 生產流程相同，因此強制歸 V1 統計，避免 V3 數字虛高。

### V2 — 出貨行政流程

- 任務代碼以 `V2` 開頭
- NPE 廠區的 V2 出貨任務維持 V2（不受上述 NPE 規則影響）

### V3 — 品質異常流程

- 任務代碼以 `V3` 開頭（且不屬於 NPE 廠區的非出貨任務）

## 八、驗證步驟建議

以「V2 / CNE / WJ2 / 2026-04 月報 Done 數量」為例：

1. 確認你要驗證的是哪個環境（dev/qas/prd），從對應 S3 環境下載 `2026-04_CNE_WJ2_V2.csv.gz`
2. 解壓縮後另存為 `.xlsx`
3. **先篩 `in_month_cohort = 1`**（月報驗證必要條件，見第四節）
4. 再篩 `status_monthly = DONE`
5. 計算篩選後的筆數，應與月報該線別的 Done 數字一致

若數字有差異，請先確認：
- 是否忘記篩 `in_month_cohort = 1`（最常見的錯誤，會導致數字偏高）
- 篩選的是 `status_monthly` 而非 `status_daily` 或 `task_status`
- 是否比對到不同環境（dev/qas/prd）的檔案
- 2026-04-01 之前的月份，日粒度驗證是否用了「開單/簽收/完工任一天」的邏輯，而非只看開單日

## 九、欄位速查

| 欄位名稱 | 說明 |
|---|---|
| `task_id` | 任務唯一識別碼 |
| `proc_inst_id` | 流程實例 ID（同一工單可能包含多個任務） |
| `task_name` | 任務名稱（如：組裝、測試、包裝） |
| `task_start_date` | **開單日（KPI 時間基準）** |
| `task_claim_date` | 簽收日 |
| `task_end_date` | 完工日（空白 = 尚未完工） |
| `status_daily` | 日報結算狀態：TODO / DOING / DONE |
| `status_weekly` | 週報結算狀態：TODO / DOING / DONE |
| `status_monthly` | 月報結算狀態：TODO / DOING / DONE |
| `in_month_cohort` | **1 = 本月開單；0 = 別月開單、本月補列**（見第四節，週/月驗證必看） |
| `file_month` | 這一列所屬的檔案月份（除錯用） |
| `vx_type` | 業務分類：V1 / V2 / V3 |
| `region` | 區域：CNE / CNS / CNW |
| `plant` | 廠別 |
| `factory` | 工廠 |
| `line` | 線別 |
| `mo_number` | 工單號 |
| `model_name` | 機種 |
| `assignee_name` | 處理人姓名 |
| `duration_min` | 開單到完工的總時長（分鐘），未完工為空白 |
| `processing_time_min` | 簽收到完工的實際處理時長（分鐘） |
