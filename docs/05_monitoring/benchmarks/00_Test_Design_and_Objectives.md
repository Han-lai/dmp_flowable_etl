# ClickHouse 資料倉儲效能驗證：設計與目的 (Test Design & Objectives)

本章節旨在說明 L5 流程分析系統中，引入 ClickHouse 作為資料分析核心的架構驗證思路。與傳統資料庫的測試不同，本校閱重點在於驗證「列式儲存 (Columnar Storage)」在海量計算場景下的真實優勢。

## 1. 測試目的 (Testing Objectives)

### 1.1 為什麼需要驗證 ClickHouse？
在原始架構中，報表數據直接由 MSSQL (行式資料庫) 提供。隨著歷史數據累積，分析查詢（如：計算過去一年的週達成率）會涉及大量的 I/O 掃描，導致報表呈現延遲。我們引入 ClickHouse 的核心目的是：
*   **計算與存儲分離**：將 OLTP (MSSQL) 的事務負載與 OLAP (ClickHouse) 的分析負載分離，確保不會因報表查詢影響生產系統。
*   **極致查詢速度**：驗證 ClickHouse 在處理千萬級數據時，是否能在秒級甚至亞秒級回傳結果。

### 1.2 與傳統資料庫 (如 MSSQL) 在報表場景的差異
傳統 MSSQL 採用 **行式儲存 (Row-oriented)**，在讀取特定的 5 欄指標時，仍需將整行（可能包含 50 欄以上）的資料全部讀入記憶體，造成大量的 I/O 浪費。
ClickHouse 採用 **列式儲存 (Column-oriented)**，查詢指標時僅讀取涉及的列，且同類數據相鄰儲存，能實現極高的壓縮比與掃描效率。本次測試旨在量化這種架構轉換帶來的效能紅利。

## 2. 測試設計原則 (Test Design Principles)

### 2.1 為什麼選擇「真實報表 SQL」作為測試？
我們不使用簡單的 `SELECT count(*)`，而是直接抽取 **Apache Superset 產生的真實 Pivot SQL**。
*   **理由**：Superset 產生的 SQL 包含多層 CTE (Common Table Expressions) 與 `UNION ALL` 行列轉置。這類語法對資料庫的解析器與執行計畫是極大挑戰。唯有通過真實 SQL 的測試，方能代表使用者端感受到的真實語義層（Cube.js）延遲。

### 2.2 為什麼模擬「多使用者併發」？
*   **理由**：單一查詢的速度（Latency）並不代表系統能力。在實際業務中，多位管理人員可能同時刷新儀表板。模擬 **10 人併發 (Concurrency 10)** 是為了觀察 ClickHouse 在高負載下是否會出現鎖（Lock）競爭或記憶體崩潰，並找出其「併發轉折點」。

## 3. 測試比較重點 (Evaluation Metrics)

在評估 ClickHouse 表現時，我們依據以下四項指標判定架構優勢：

1.  **查詢回應時間 (Latency)**：
    *   **P50 中位數**：50% 的使用者感受到的平均查尋速度。
    *   **P95 長尾延遲**：最慢的 5% 查詢，用以觀察極端案例（如跨年大範圍查詢）的穩定性。
2.  **併發查詢能力 (Concurrency Capability)**：
    *   在高併發下，查詢延遲是否呈現線性增長而非指數級飆升。
3.  **壓縮率 (Compression Ratio)**：
    *   **核心量化指標**：`原始資料大小 / 實際存盤大小`。高壓縮率不僅節省硬碟，更意味著更少的磁碟 I/O 讀取。
4.  **查詢吞吐量 (QPS - Queries Per Second)**：
    *   系統每秒能處理完成的查詢次數，反映資料倉儲的整體「吞吐規模」。

## 4. 測試情境說明 (Test Scenario)

所有壓測均在以下場景中執行，以貼近日常維運狀態：

*   **動態日期範圍**：模擬使用者查詢「上週」、「本月」或「特定 7 天」等隨機變化的日期區間。這能測試 ClickHouse 緩測機制外，對磁碟分區 (Partitioning) 的隨機讀取能力。
*   **標準與複雜 SQL 對比**：同時測試「純聚合 (Standard)」與「行列轉置 (Pivot)」兩版 SQL，藉此量化語義轉化層（Cube.js）帶來的額外負載係數。
*   **全層級資料覆蓋**：測試範圍涵蓋 Bronze (原始檔)、Silver (清洗後)、Gold (指標快照)，確認各層級資料在不同物理結構下的讀取效能。

---

**結論**：本次驗證不只是追求數據，而是要透過數據，確認 ClickHouse 的列式引擎是否能完美銜接 L5 流程分析的業務擴展需求。
