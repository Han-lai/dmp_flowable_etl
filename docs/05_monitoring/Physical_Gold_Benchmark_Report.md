**測試日期**: 2026-04-13

**伺服器規格**: 11 GiB Memory (Docker 容器環境)

## 1. Background & Architecture Evolution

### 1.1 Legacy Architecture and Observed Issues
於系統上線初期，報表底層採用「動態視圖 (On-the-fly View)」架構。前端商業智慧工具 (Superset) 在顯示 L5 報表時，資料庫必須在讀取當下即時運算 Todo/Doing/Done 的狀態分佈，並同時混算最耗能的 7 日滾動在途任務 (ACC 包含跨日去重的 `uniqExact` 邏輯)。
此架構在面臨多併發存取時，會迫使 ClickHouse 於單一查詢內耗盡大量記憶體來維持這些即時狀態交集。當併發連線數累積增加時，系統資源即迅速陷入匱乏，引發記憶體耗盡錯誤 (Out-Of-Memory, OOM)，並導致前端面臨大面積 Timeout 異常。

### 1.2 Performance Characteristics (Before Optimization)
在舊有動態視圖 (Dynamic View) 架構下，針對 10 併發進行之基準測試，其核心效能表現極其受限：

| 評估指標 | 實測數值 (10 Concurrency) | 效能特徵 |
| :--- | :--- | :--- |
| **QPS 吞吐量** | 10.5 ~ 12.4 | 受限於單次高負載運算，整體吞吐量極低 |
| **Peak RAM** | 404.10 MiB / 次 | 單次查詢即佔用大量記憶體，百人請求需近 40 GiB 資源 |
| **Latency** | P95=1.20s / P99.9=1.34s | 長尾延遲嚴重影響應用層體驗 |
| **Error Rate** | 高併發時 100% Timeout | 系統遭遇連線峰值即刻崩潰 |

### 1.3 VM Migration & Observed OOM Trigger
系統初期部署於 Server 207 (測試環境)，記憶體資源充裕，Gold 層採用 Refreshable Materialized View (MVIEW) 架構運作穩定，Silver/Gold 層 MVIEW 按排程定期刷新，未出現資源瓶頸。

後續因環境調整，系統遷移至 Server 76 生產環境，Docker 容器可用記憶體僅 **4.5 GB**。在此受限環境下，MVIEW 於高併發存取時因即時聚合 Milestone 與 ACC (`uniqExact` 跨日去重) 之運算需求超出硬體容量，觸發 OOM。

MVIEW 架構本身並無設計缺陷。若部署環境之記憶體資源充足 (建議 16 GB 以上)，MVIEW 仍為可行方案。

### 1.4 Architectural Transition to Physical Gold Design
基於 Server 76 之硬體限制，系統決策為：將 Milestone 與 ACC 的計算邏輯「完全脫鉤 (Decoupling)」，全面轉向「實體化金層架構 (Physical Gold Layer)」。
本決策將原先沉重的即時運算，全數移轉至背景 ETL 批次處理環節。ETL 流程被重構為：
1. 階段 4：獨立計算 `gold.rmv_l5_milestone_phys`，避免多重 JOIN 負擔。
2. 階段 5：獨立計算 `gold.rmv_l5_acc_phys`，專心處理 7 天滾動去重。
3. 階段 6：最終合併為 `gold.rmv_l5_task_completion_phys`。
此架構使前端查詢僅需執行單純之索引讀取，徹底免除 On-the-fly 計算負擔，並根除了記憶體溢出危機。

### 1.6 Performance Improvement Summary
架構轉變實體化設計後之效能提升對比，驗證此技術轉型完全解決了既有問題：

| 指標檢視 | Before (單表動態視圖) | After (拆分實體化架構) | 改善幅度判定 |
| :--- | :--- | :--- | :--- |
| **QPS** | 10.5 ~ 12.4 | **84.58** | 基準處理量提升 **8.05 倍** |
| **Peak RAM** | 404.10 MiB | **< 5 MiB** | 消耗足跡顯著降低逾 **98%** |
| **P99 Latency** | 1.34 秒 | **0.61 秒** | 延遲減半，大幅優化用戶體驗 |
| **系統可用性** | >50併發即引發 OOM | **100併發 100% 成功運算** | 徹底杜絕中斷與 Timeout 異常 |

## 3. 大數據環境下之硬體資源消耗與擴展性評估 (Resource Utilization & Scalability)

為評估新架構在大數據處理量下之抗壓能力，本節實測單次報表查詢之資源軌跡如下：

| 資源指標 | 實測數值區間 | 實體伺服器佔用率 | 評估意義 |
| :--- | :--- | :--- | :--- |
| **平均記憶體佔用 (Avg RAM)** | 3.84 ~ 3.99 MiB | **~ 0.034%** | 基礎查詢時之記憶體耗用水準 (基準: 11 GiB) |
| **峰值記憶體佔用 (Peak RAM)** | 4.38 ~ 4.97 MiB | **最高 0.044%** | 滿載狀態下之極限記憶體消耗佔比 |

## 6. 綜合驗收結論 (Executive Summary)

經綜合效能、資源、儲存與邏輯等四大構面之深度驗證，ClickHouse 實體化架構皆取得優異成果：

1. **效能破局**：徹底消解即時運算瓶頸，將 P99 查詢延遲穩定收斂於 1 秒內。
2. **容量與擴展**：憑藉逾 30 倍壓縮比及低於 5 MiB 的微幅記憶體耗用率，系統可穩固擴展至十億級資料量。
3. **系統防禦**：連線排隊機制部署獲實證，有效攔截 DDoS 異常並保證服務可用率。
