# 實作手冊 5：系統效能基準測試與調優建議報告

本手冊彙整了 ClickHouse 在 L5 報表場景下的實際效能表現，並提供維運優化建議。所有數據均來自 2026-03-06 的實測紀錄。

---

## 1. 查詢效能實測 (Query Latency)
我們針對「Pivot 報表」與「基礎聚合」兩類 SQL 進行了對比測試。

### **1.1 延遲詳情與長尾分佈 (Percentile Breakdown)**
針對 **10 併發、100 次循環** 的壓測，我們觀察到以下長尾延遲分佈：

| 查詢模型 | P50 (中位數) | P95 (長尾) | P99.9 (極端) | QPS (吞吐) |
| :--- | :---: | :---: | :---: | :---: |
| **Pivot Model (報表)** | **0.87 秒** | **1.20 秒** | **1.35 秒** | 10.5 ~ 12.4 |
| **Standard Model (運算)** | **0.14 秒** | **0.20 秒** | **0.26 秒** | 51.4 ~ 62.2 |

*   **系統瓶頸分析**：Standard Model 的極速表現證明 ClickHouse 核心運算極強。Pivot Model 的 0.8s 延遲中，約 80% 時間消耗於報表所需的行列轉置（UNION ALL）操作，而非物理讀取瓶頸。

### **1.2 即時資源消耗 (Per-Query Resources)**
根據 `system.query_log` 的 786 個樣本統計：
*   **CPU User Time**: 平均 **258 ms** (單核耗時)。
*   **Memory Usage**: 平均 **241 MiB**, 峰值 **404 MiB**。
*   **結論**: 系統對 VM 的資源佔用極低，在高併發下依然維持低記憶體軌跡。

## 4. 維運優化建議
*   **CPU 卸載**：若未來併發使用者超過 50 人，建議將 Pivot 轉置邏輯從 SQL 移至 FastAPI 處理，可直接提升 QPS 約 4 倍。
*   **冷熱分離**：建議針對 `Bronze` 層設定 TTL，保留 1 年數據即可，其餘歷史數據可歸檔至冷存儲。
*   **資源監控**：建議在 Grafana 觀察 `ClickHouse CPU User Time`，若平均超過 500ms 表示 SQL 轉置壓力較高。
