## 第一章：系統概覽（Ch.1 / 約 3 分鐘）

在開始之前，先說明這個系統誕生的背景，以及它的整體架構長什麼樣子。

我們原本的做法，是直接在 MSSQL 上用 Stored Procedure 跑報表聚合。早期資料量小沒有問題，但隨著資料量成長，兩個核心問題開始浮現：第一是**資源競爭**——分析查詢跟線上交易搶同一批資源，導致生產端連線逾時；第二是**計算複雜度**——像是多維度精確去重、7 天滾動在途任務量這類指標，MSSQL 在千萬筆資料面前效率極低。

這個專案的核心目標因此非常明確：把分析負載從 MSSQL 遷移到 ClickHouse，透過 **Medallion 三層架構**實現毫秒級的多維度查詢回應。

*（可搭配 1.2 的架構拓撲圖）*

整體架構的資料流向是這樣的：資料從 MSSQL 的兩個來源系統出發——BPM 流程引擎存任務紀錄，Common 系統存人員和組織主檔。資料透過 ODBC 直傳進 ClickHouse，先在 **Bronze 層**原始落地，再往上走到 **Silver 層**清洗轉置，最後在 **Gold 層**完成 Bitmap 指標預計算。前端的 Cube.js 只對 Gold 層查詢，不直接碰底層資料庫。

整條管線遵循一個核心原則：**Python 負責指揮，ClickHouse 負責搬運**。Python 腳本只做排程控制，真正的資料搬運由 ClickHouse C++ 引擎直接執行，資料不流經 Python 記憶體，這是達到高吞吐的關鍵。

## 第二章：管線驅動（Ch.2 / 約 2 分鐘）

整條管線由三支 Python 腳本依序驅動，分工清楚。

**第一支 `setup_schema.py`** 是一次性部署工具，負責在 ClickHouse 建立 Bronze、Silver、Gold 三層的所有表結構。它是冪等的，可以安全重跑。

**第二支 `sync_unified_odbc.py`** 每日排程執行，把 MSSQL 的資料批次同步到 Bronze 層。透過浮水印機制記錄上次同步進度，確保不遺漏、不重複。

**第三支 `execute_etl.py`** 在 Bronze 落地完成後接手，負責驅動 Silver 和 Gold 的所有運算。Silver 完成才接著跑 Gold，靠的是程式碼的順序保證，不是額外的狀態查詢機制。

三支腳本串起來，就是整條管線每天自動執行的骨架。接下來我們看每一層實際在做什麼，從資料最先落地的 Bronze 層開始。

---

## 第三章：Bronze Layer（Ch.3 / 約 1.5 分鐘）

Bronze 層的定位是**原始資料倉**，任務只有一件事：把 MSSQL 的資料 1:1 落地，不做任何業務轉換，徹底隔離生產環境與分析系統。

這一層採用 ClickHouse 的 `ENGINE = ODBC(...)` 機制，在 ClickHouse 內部建立指向 MSSQL 的虛擬代理表，再透過 `INSERT INTO ... SELECT FROM` 讓 C++ 引擎直接高速拉取。資料不流經任何中間層，這是達到每秒九萬筆以上吞吐量的關鍵。

表格引擎採用 `ReplacingMergeTree`，背景 Merge 時自動依版本號去重，保留最新的那一筆，不需要 Upsert 邏輯，重傳也能自動修復。另外有一張浮水印追蹤表，記錄每張表最後同步到的時間戳，確保每日增量不遺漏。

同步策略分兩種：大型流水表用批次增量、小型維度表用全量同步。

Bronze 層到這裡，資料已經安全落地。但原始資料的格式還不能直接用來算指標，接下來 Silver 層要做的就是把這些資料清洗整理成可以計算的形狀。

## 第四章：Silver Layer（Ch.4 / 約 2 分鐘）

Silver 層的工作是把 Bronze 的原始資料清洗、轉置，最終產出三張表。

**第一張 `mv_varinst_pivoted`**：BPM 引擎把流程執行環境以 EAV 結構垂直存放，同一個流程會有很多列。這張表把它轉成寬表，每個流程實例壓縮成一列，方便後續 JOIN。

**第二張 `mv_dim_mfg_five_level`**：五階維度主檔，透過四張 MDM 表連鎖 JOIN，建立從線體到地區的完整對應關係。這張表是一次性初始化，不走每日排程，只有 MDM 主檔異動時才重建。

**第三張 `mv_fact_task_vx`**：Silver 層最核心的輸出，把前兩張表與任務原始資料整合在一起，寫入時同步完成三件事：第一，判斷任務屬於哪個 Vx 製程版本；第二，把廠區維度對齊到五階層級；第三，標記哪些任務排除在 KPI 之外。Gold 層所有的計算，都以這張表為唯一起點。

Silver 層把資料整理好了，交棒給 Gold 層。Gold 層要做的事只有一件：把指標算出來，存起來，讓前端查詢的時候直接拿結果。

---

## 第五章：Gold Layer（Ch.5 / 約 3 分鐘）

Gold 層的核心概念只有一句話：**把所有耗時的計算，在資料寫入的時候就做完，查詢的時候直接讀結果。**

傳統做法是每次查詢才去掃描千萬筆明細、即時去重，這樣很慢。Gold 層改變了這件事——每天 ETL 跑完，指標就已經算好存進資料庫了，前端只是去讀一個數字。

做到這件事的關鍵是 **Bitmap 位圖**。每一筆任務用一個 bit 來代表，要知道有多少筆不重複的任務，做一次位圖的聯集運算就夠了，速度遠超傳統的 COUNT DISTINCT。

具體的計算分三步走：

第一步，**Milestone 展開**。每筆任務有三個重要時間點——啟動、認領、結案。我們把這三個時間點展開成每日的快照，依照任務當天的狀態，分別寫進 Todo、Doing、Done 三個位圖裡。

第二步，**ACC 展開**。ACC 是累積在途量，代表過去七天內有活動但還沒結案的任務數。這裡用 ARRAY JOIN 把每筆任務的活動區間展開成每天一列，預先寫進 ACC 位圖。這樣查詢時不需要任何視窗計算，一次讀取就有答案。

第三步，**合併主表**。把前兩步的結果合併在一起，產出最終的統一主表，Cube.js 就是從這張表取數據。

另外，Gold 層的寫入有 Checkpoint 保護。每個時間視窗成功後會記錄狀態，中途中斷可以直接從上次停的地方繼續，不需要重跑；萬一記憶體不足，視窗會自動切小再重試。

## 第六章：Serving Layer（Ch.6 / 約 1.5 分鐘）

資料算好之後，BI 前端透過 **Cube.js 語義層**來取用，它的角色是一個統一的查詢入口——把底層的 ClickHouse 細節封裝起來，對 BI 工具只暴露標準的指標 API。

一般的 Dashboard 和 KPI 趨勢，都直接讀 Gold 層，因為數字已經預算好，回應非常快。如果需要下鑽到任務明細、或是臨時的 Ad-hoc 查詢，才會走到 Silver 層來撈原始資料，兩條路各司其職。

日常調度這邊，每天由一支封裝腳本自動執行：先刷新 Bronze 層的浮水印，再依序觸發 Silver 和 Gold 的運算。如果數字有疑問，可以用稽核腳本帶入日期和產線參數，直接把 Silver 層的任務明細匯出成清單來做對帳。

我們直接用實際畫面來看一下這兩條查詢路徑是怎麼運作的。

*【Demo 1 — Dashboard 篩選】切換到 Superset / BI Dashboard，選擇廠區與日期區間，展示 Gold 層的快速回應，觀察各指標數字即時更新。*

*【Demo 2 — 明細查詢】切換到 DBeaver 或終端機，執行稽核腳本，帶入指定日期與產線，輸出任務明細清單，說明這就是 Silver 層直查的結果。輸出欄位包含：任務 ID、啟動 / 認領 / 結案時間、任務狀態、Vx 版本、五階維度（Region / Plant / Factory / Line）、是否排除及原因、負責人代碼與姓名、任務定義 Key、工單號，以及流程實例 ID，涵蓋稽核所需的完整脈絡。*

## 第七章：效能與運維（Ch.7 / 約 2 分鐘）

最後用數字說明架構的實際效果。

首先是資料傳輸與儲存這塊。我們之前用 Airbyte 做資料同步，速度和穩定性都有一定的限制。換到 ClickHouse 的 ODBC 直傳模式之後，差距非常明顯——同樣的資料，吞吐速度達到每秒超過 **12 萬筆**，整條管線在 **10 分鐘內**就能處理超過 5,290 萬筆。不只快，ClickHouse 的列式壓縮也很顯著，以其中一張表為例，原本在 MSSQL 佔了 4 GB 多，壓縮進 ClickHouse 之後只剩 130 MB 左右，壓縮比將近 32 倍，存儲成本大幅降低。

查詢這邊，因為 Gold 層已經把指標預算好，前端在 100 人並行的高壓情境下，L5 任務指標的回應時間仍然維持在 **0.4 秒以下**，這是傳統即時聚合做不到的。

最後一點也是這個三層架構設計的彈性所在：如果業務邏輯調整，或是發現某一層的計算有問題，不需要把整個資料庫重跑。Bronze、Silver、Gold 各自獨立，可以單獨針對某一層做修正或重算，甚至可以切分特定時間範圍重跑，不影響其他層的資料。這讓維運和迭代的成本都大幅降低。

## 結語（約 1 分鐘）

做個總結。

這套系統從一個很具體的問題出發：MSSQL 的分析負載壓垮了生產環境，而且指標越來越複雜，舊架構根本算不動。我們用 Medallion 三層架構來解這個問題——Bronze 把原始資料安全隔離落地，Silver 清洗轉置成可計算的結構，Gold 在 ETL 時就把所有指標算好，查詢時直接讀結果。

這樣的設計帶來兩個核心優勢：第一是效能——毫秒級的查詢回應、高壓下穩定的表現；第二是彈性——三層各自獨立，業務邏輯要調整、或是某層要重算，都不需要動整個資料庫，維運成本大幅降低。

整套架構目前已在正式環境穩定運行，歡迎大家有任何問題繼續交流，謝謝。
